# BENCHMARK

数字一律实测。每组数字都写明环境、命令和跑了几次;没复现过的不写。

## 结论先看

500 条连接、63 个房间、每秒入站 12,500 条 / 出站 12,500 条消息。同一个负载在两条网络路径上各跑 3 次:

| 指标 | 容器内 loopback | 宿主机 127.0.0.1(绕经 Windows) | 门槛 |
|---|---|---|---|
| Ping RTT p99 | 0.44 / 0.46 / 0.52 ms | 1.08 / 1.32 / 1.40 ms | ≤ 12 ms |
| 快照间隔 p99(客户端看到的 20Hz 节拍) | 51.11 / 51.11 / 51.21 ms | 51.40 / 51.59 / 51.64 ms | ≤ 55 ms |
| 快照到达率 | 99.989% / 100.002% / 100.000% | 100.001% / 100.000% / 100.000% | ≥ 99.9% |
| 服务端 tick 耗时 p99 | 10–25 / 25–50 / 25–50 µs 桶 | 25–50 µs 桶(插值约 49 µs) | < 1 ms |
| 失败 / 中途断线 | 0 / 0 | 0 / 0 | 0 |
| 服务端 CPU | 0.43–0.57 核 | 约 0.5 核 | 只记录 |

- **两条路径差 3 倍,差在网络,不在程序**。这台 WSL2 开着 mirrored 网络模式,宿主机上连 127.0.0.1 的 TCP 不走内核的 `lo`,而是经 `loopback0` 网卡绕到 Windows 再回来;容器有自己的网络命名空间,走的是真正的内核 loopback。同一个二进制换路径就差 3 倍,对照实验和路由表见[网络路径](#网络路径b62)。
- **拐点**:容器内 loopback 在 8000–10000 连接之间(8000 连接快照间隔 p99 54.8 ms,10000 连接 60.2 ms,到达率一直是 100%);走 127.0.0.1 时在 2000–3000 之间,先撑不住的是那条绕路(见[拐点](#拐点b57))。
- 第一版压测客户端的 Ping p99 是 11 ms,原因在客户端:500 个 bot 的发送相位对齐,每 50 ms 一波突发。加随机相位之后是 1.1–1.4 ms(见[第一版](#第一版相位对齐的压测客户端))。
- 容器:运行镜像压缩后 9.8 MB;`docker compose up` 到第一个 bot 登录成功,数据卷已存在时 2.1 s,第一次(MySQL 要初始化)8–9 s(见[容器](#容器b6))。

## 压测(B5)

### 方法

负载模型:

| | 值 | 说明 |
|---|---|---|
| 连接 | 500 | 全部登录后快速匹配,进 63 个房间(62 × 8 + 1 × 4) |
| 每个 bot | 20 MoveInput + 5 Ping / s | Ping 按 ticker 发,不等上一个 Pong(open-loop,避免 coordinated omission);开始前等一个 0–200 ms 的随机相位 |
| 入站 | 12,500 msg/s | 500 × 25 |
| 出站 | 12,500 msg/s | 500 × (20 快照 + 5 Pong) |
| 时长 | 预热 5 s + 测量 30 s | 只统计测量窗口内到达的样本 |
| 分位数 | 最近秩 | `sorted[ceil(p·n) − 1]`,不插值(D23) |

```bash
make build
./bin/gameserver -addr 127.0.0.1:17777 -admin 127.0.0.1:19100 -log-level warn &
./bin/botclient -addr 127.0.0.1:17777 -c 500 -d 30s -warmup 5s
```

压测开始 10 s 和 20 s 时各抓一次 `/metrics`,两次相减得到这 10 s 的速率和直方图;bot 退出 2 s 后再抓一次看是否归零。服务端日志级别 warn(每条连接的上下线日志不进热路径)。

### 结果:客户端视角(B5.1–B5.3)

| 1 | 375 µs / 1.315 ms / 4.12 ms | 50.00 / 51.59 / 53.89 ms | 300,002 / 300,000 | 0 / 0 |
| 2 | 353 µs / 1.402 ms / 5.51 ms | 50.00 / 51.64 / 54.11 ms | 300,000 / 300,000 | 0 / 0 |
| 3 | 362 µs / 1.075 ms / 2.97 ms | 50.00 / 51.40 / 52.89 ms | 299,999 / 300,000 | 0 / 0 |
| **中位数** | **362 µs / 1.315 ms / 4.12 ms** | **50.00 / 51.59 / 53.89 ms** | **100.000%** | |

每次 75,000 个 RTT 样本、约 30 万个快照间隔样本。实收比期望多一两个,是测量窗口边界的效果:30 s 的窗口里一个 50 ms 周期的事件出现 600 或 601 次。

### 结果:服务端视角(B5.4、B5.5,T5.3–T5.5)

压测第 10–20 s 的 `/metrics` 差值:

| 次 | 在线 / 房间 | 入站 msg/s | 出站 msg/s | tick 次数/s | tick 耗时 p50 / p99 | tick 准点 p50 / p99 |
|---|---|---|---|---|---|---|
| 1 | 500 / 63 | 12,507 | 12,503 | 1,260.4 | 5–10 µs 桶(≈8.5) / 25–50 µs 桶(≈49.6) | 100–250 µs 桶 / 1–2 ms 桶 |
| 2 | 500 / 63 | 12,505 | 12,501 | 1,260.0 | 5–10 µs 桶(≈8.3) / 25–50 µs 桶(≈48.9) | 100–250 µs 桶 / 1–2 ms 桶 |
| 3 | 500 / 63 | 12,505 | 12,504 | 1,260.4 | 5–10 µs 桶(≈8.6) / 25–50 µs 桶(≈49.8) | 100–250 µs 桶 / 1–2 ms 桶 |

- T5.3:压测中 `gameserver_players_online` = 500,`gameserver_rooms` = 63。
- T5.4:入站 counter 增速 12,505–12,507/s,期望 12,500(+0.06%)。其中 MoveInput 10,004/s、Ping 2,501/s;出站快照 10,000–10,003/s、Pong 2,501/s。
- T5.5:tick 直方图 `_count` 增速 1,260.0–1,260.4/s,期望 63 × 20 = 1,260。
- 括号里是桶内线性插值的估计,精度只到桶(D22)。tick 耗时比微基准 B4.3(0.87 µs)大一个数量级。微基准里投递是空操作;真实负载下要往 8 个 channel 发送、唤醒 8 个写 goroutine,还可能等读 goroutine 放房间锁,多出来的时间应该在这里(没有单独拆)。即使如此,p99 也只用了 50 ms 预算的 0.1%。
- tick 准点和空载对比(B4.1:p50 0.56–0.60 ms,p99 1.1–1.6 ms):满载时 p50 反而更低(100–250 µs)。我的解释是空载时线程都睡着了,tick 到点要先叫醒一个线程;满载时总有线程醒着,timer 到点能直接被调度。p99 两者都在 1–2 ms。

### CPU 火焰图(T5.7)

压测中用 admin 端口抓 30 s CPU profile:

```bash
curl -o cpu.pb.gz 'http://127.0.0.1:19100/debug/pprof/profile?seconds=30'
go tool pprof -http=:8080 bin/gameserver cpu.pb.gz   # 浏览器里 View → Flame Graph
```

原始 profile 在 [`profiles/cpu-500c-30s.pb.gz`](profiles/cpu-500c-30s.pb.gz),下图是它的静态渲染(`go tool pprof -traces` 折叠成栈后画成 SVG):

![500 连接 30 秒 CPU 火焰图](img/flamegraph-500.svg)

30 s 里采到 15.72 s,平均 0.52 个核。最宽的三个栈:

1. **调度器:`runtime.mcall → schedule → findRunnable`,63%**。其中 `futexwakeup` / `notewakeup` / `startm` 是在唤醒睡眠的 OS 线程,`injectglist` 是把 netpoller 就绪的 goroutine 放回运行队列。1,000 多个 goroutine 每个每秒被唤醒 20–25 次,每次都可能要叫醒一个线程,这就是「很多很轻的活」的代价。
2. **读循环:`gateway.(*Conn).readLoop`,23.6%**。read 系统调用约 7%,protobuf 解码约 5.5%,大厅处理 MoveInput 1.9%,`SetReadDeadline` 约 1%。
3. **写循环:`gateway.(*Conn).writeLoop`,10.3%**,几乎全是 write 系统调用(一帧一次 Write)。

业务代码(tick、大厅、编解码、metrics)加起来不到 15%:tick 2.2%,metrics 计数 2.2%(按类型计数用了 protobuf 反射 `WhichOneof`,和 tick 一样贵,是一个能省的点),编码 1.7%。CPU 主要花在系统调用和线程的睡眠 / 唤醒上,所以要扛更多连接,方向是减少系统调用和唤醒次数(写循环把积压的帧合并成一次 `writev`),而不是优化游戏逻辑。

这张图是走 127.0.0.1 时抓的。在容器里(bot 也在容器里,内核 loopback)同样的负载再抓 30 s([`profiles/cpu-500c-30s-container.pb.gz`](profiles/cpu-500c-30s-container.pb.gz)):采到 10.75 s,平均 0.36 个核;调度器 58%(其中 `futex` 37%),读循环 23%,写循环 16%,系统调用 21%。结构和上面一样,调度器仍是大头;少掉的 0.16 个核主要是 `futex` 和 `notewakeup`,也就是叫醒线程的次数少了。

### 第一版:相位对齐的压测客户端

第一版 botclient 在同一个循环里给 500 个 bot 建 ticker,所有 bot 的发送时刻是对齐的。完整跑一次(30 s,和上面同一个负载)的结果:

| | Ping RTT p50 / p99 / max | 快照间隔 p99 | 服务端 tick 准点 p50 |
|---|---|---|---|
| 相位对齐(第一版) | 4.05 / 10.99 / 12.72 ms | 51.39 ms | 250–500 µs 桶 |
| 随机相位(现在) | 0.35–0.38 / 1.08–1.40 / 3.0–5.5 ms | 51.40–51.64 ms | 100–250 µs 桶 |

当时服务端只用了 0.42 个核、bot 0.66 个核,却有 4 ms 的 RTT 中位数,说明时间不是花在计算上。按连接数扫一遍(每档测 8 s)就清楚了:

| 连接数 | 相位对齐 RTT p50 / p99 | 随机相位 RTT p50 / p99 |
|---|---|---|
| 1 | 338 µs / 600 µs | 324 µs / 622 µs |
| 50 | 922 µs / 1.78 ms | 255 µs / 547 µs |
| 200 | 2.13 ms / 4.77 ms | 262 µs / 738 µs |
| 500 | 4.55 ms / 12.73 ms | 370 µs / 1.26 ms |

相位对齐时 RTT 随连接数线性增长:每 50 ms 有 500 条消息在同一瞬间到达,服务端和 bot 都要先把这一波排队消化完,量到的主要是排队时间。真实玩家的发送时刻是随机的,压测客户端也应该是(D23)。在找到原因之前,还试过把两边的 `GOMAXPROCS` 在 2 / 4 / 20 之间组合(每种测 10 s):对齐时 RTT p50 在 2.6–5.6 ms 之间,没有一种回到 0.4 ms,说明不是「核太多、调度器空转」的问题。

**拐点在 8000–10000 之间**。10000 是第一个不过的档,快照间隔 p99 60.2 ms,刚过线。整个过程到达率始终 100%,没有断线,服务端 tick 耗时 p99 一直在 25–50 µs 桶。先劣化的是尾延迟:RTT p99 从 6000 档的 1.6 ms 涨到 10000 档的 8 ms。

- 这时服务端 6.1 核、bot 6.6 核,两个进程合计 12.7 核,机器是 20 个逻辑核(6 个 P 核带超线程 + 8 个 E 核),已经在抢 CPU。有多少延迟是 bot 自己的,分不开。
- 种子账号只有 1–10000,再往上的 bot 登录会被拒(`NO_ACCOUNT`),所以这套测法在这台机器上到 10000 为止。
- 内存随连接数线性涨,每多 1000 条连接 RSS 多约 46 MiB。

走这条路时,拐点在 2000–3000 之间:3000 档的快照间隔 p99 已经 146 ms,而容器里 3000 档还是 51.3 ms。程序和负载都一样,差别只在网络路径(B6.2),所以旧表量到的主要是 WSL mirrored 那条绕路的上限,不是服务端的上限。

当时据此写的「先崩的是每条消息一次系统调用 + 一次唤醒的调度开销,CPU 还有余量」,只对那条路成立。依据是 3000 档另抓的 15 s profile:服务端 2.9 核,系统调用 34%、`findRunnable` 40%、`futex` 24%,大厅和编解码加起来不到 10%。容器里的 profile 结构相同(见火焰图一节),但同样的连接数下尾延迟低得多。

下一步按收益排:写循环合并积压的帧(`net.Buffers` / `writev`),减少写系统调用;快照和 Pong 合并发送;metrics 计数改成类型 switch,去掉反射;再往上(上万连接)才考虑 epoll 事件循环替代 goroutine-per-connection。

## 容器(B6)

`make up` 起全套:gameserver + `redis:7.4-alpine` + `mysql:8.4`,都在 compose 的默认 bridge 网络里。2026-10-11 第一次在 Docker 上跑,下面这些一次就全部跑通:

- 镜像构建、MySQL 建表、healthcheck;
- 登录和账号校验(玩家 20000 不在种子账号里,被拒 `NO_ACCOUNT`);
- 两个客户端互相看见,战绩写进 MySQL;
- `--profile monitoring` 起的 Prometheus 抓到了 gameserver(target 状态 `up`)。

### 镜像(B6.1)

| | 大小 |
|---|---|
| 压缩后(推送 / 拉取时传输的大小) | 9.8 MB |
| 解压后 | 27.8 MB:三个二进制 22.4 MB + distroless/static 基础层 5.4 MB(其中时区数据 4.2 MB) |

`docker images` 显示的 `DISK USAGE` 是 37.6 MB:用 containerd 存镜像时,压缩包和解压后的文件各存一份,这个数是两者之和。同一口径下 `mysql:8.4` 是 1.12 GB,`redis:7.4-alpine` 是 57.8 MB。第一次构建:`go mod download` 2.4 s,编译三个二进制 7.5 s。

### 网络路径(B6.2)

服务端放在容器里,bot 分别从三个位置连进去,再和裸跑对比。负载同 B5(500 连接),Redis 和 MySQL 都用 compose 里的。四种跑法交替进行、各跑 3 次,这样机器状态有漂移时,四种受到的影响一样:

| 路径 | Ping RTT p50 | p99 | max | 快照间隔 p99 | 服务端 CPU | 另外的 CPU |
|---|---|---|---|---|---|---|
| 裸跑:宿主机上两个进程,127.0.0.1 | 427–484 µs | 1.03–1.26 ms | 2.5–8.2 ms | 51.24–51.30 ms | 0.62–0.75 核 | |
| 宿主机 bot → 映射端口 127.0.0.1:7777(经过 docker-proxy) | 579–632 µs | 1.60–2.10 ms | 4.2–5.0 ms | 51.51–51.60 ms | 0.70–0.80 核 | docker-proxy 1.13–1.25 核 |
| 宿主机 bot → 容器 IP(bridge + veth) | 114–144 µs | 0.40–0.57 ms | 1.0–2.3 ms | 51.10–51.17 ms | 0.45–0.57 核 | |
| bot 在容器里(容器内 loopback) | 121–140 µs | 0.44–0.52 ms | 1.1–3.8 ms | 51.11–51.21 ms | 0.43–0.57 核 | |

12 次全部 0 失败、0 断线,到达率 99.989%–100.005%,服务端入站 / 出站都是 12,500 msg/s。每次压测结束,63 个房间解散,MySQL 里正好多 63 条战绩:12 次共 756 条,0 丢失。

**docker-proxy 很贵。** 从宿主机连映射到 127.0.0.1 的端口,数据要经过 docker-proxy 这个用户态转发进程,每条消息多一次 read、一次 write 和一次进程切换。p99 是直连容器 IP 的 3–4 倍,docker-proxy 自己用掉 1.1–1.25 个核,比游戏服本身还多。直连容器 IP(bridge + veth)和容器内 loopback 的数字几乎一样。所以在容器上压测,bot 要么放进容器里,要么直连容器 IP,不能走映射端口(D27)。

**同一个程序,裸跑反而比在容器里慢 3 倍。** 这和预期正相反,下面逐项排除:

| 对照实验(各 1 次,500 连接) | 网络命名空间 | RTT p50 / p99 | 服务端 CPU |
|---|---|---|---|
| 裸跑,宿主机编译的二进制(go1.27.1,开 cgo) | 宿主机 | 431 µs / 1.05 ms | 0.61 核 |
| 裸跑,从镜像里拷出来的二进制(go1.27.2,静态链接) | 宿主机 | 414 µs / 1.00 ms | 0.61 核 |
| 服务端在 `--network host` 的容器里,bot 在宿主机 | 宿主机 | 425 µs / 1.02 ms | 0.62 核 |
| 服务端和 bot 都在 `--network host` 的容器里 | 宿主机 | 421 µs / 1.06 ms | 0.62 核 |
| 裸跑,服务端改听 127.0.0.2 | 宿主机 | 257 µs / 0.69 ms | 0.56 核 |

- **不是二进制的问题**:Go 小版本、cgo、`-s -w` 都换过,没区别。
- **也不是容器运行环境的问题**:把进程放进 docker 的 cgroup 和 seccomp、网络留在宿主机,同样没区别。

差别只跟着网络命名空间走,原因在路由表。mirrored 模式为了让 Linux 和 Windows 共享 localhost,在宿主机的网络命名空间里加了策略路由:

```
$ ip rule
1:      from all ipproto tcp lookup 127
...
$ ip route get 127.0.0.1
127.0.0.1 via 169.254.73.249 dev loopback0 table 127 src 127.0.0.1
```

- 发往 127.0.0.1 的 TCP 先从 `loopback0` 这块虚拟网卡出到 Windows,再从 `loopback0` 收回来,不走内核的 `lo`。压测时 `loopback0` 上每秒 68,779 个包。
- 127.0.0.2 不在表 127 里,`ip route get 127.0.0.2` 给出的是 `dev lo`。服务端改听 127.0.0.2 之后,bot 发往服务端的方向走 `lo`;但 bot 的源地址还是 127.0.0.1,服务端的回包照样绕出去。`loopback0` 上的包正好少了一半(每秒 32,303 个),延迟也落在两者中间。
- 两个方向都绕、一个方向绕、都不绕(容器),RTT p50 依次是 431、257、约 130 µs。
- 容器有自己的网络命名空间,里面没有这些规则。所以容器内 loopback、宿主机连容器 IP,走的都是纯内核的路径。

结论:在这台机器上,127.0.0.1 量到的主要是 WSL 的网络开销,不是服务端的。所以正式数字两条路径都列,拐点以容器内为准(D29)。原生 Linux 上宿主机的 127.0.0.1 就是内核 loopback,预计接近容器内的数字,但没测过。

### 启动耗时(B6.3)

镜像已经构建好。从 `docker compose up -d` 开始计时,到 `botclient -player 1` 登录成功为止,每种情况跑 3 次:

| | healthcheck 只有 `interval: 5s` | 加上 `start_interval: 1s` |
|---|---|---|
| 第一次启动(`down -v` 之后,MySQL 要初始化、跑建表脚本) | 10.7 / 10.7 / 11.3 s | 9.2 / 8.2 / 9.2 s |
| 数据卷已存在(`down` 之后) | 6.2 / 6.3 / 6.2 s | 2.2 / 2.1 / 2.1 s |

- `up -d` 会等 Redis 和 MySQL 的 healthcheck 都通过才启动 gameserver,所以它返回的时刻基本就是能登录的时刻。
- 第一版只有 `interval: 5s`,第一次探测要等满 5 s:Redis 一秒内就好了,也得干等。加上 `start_interval: 1s` 后,启动阶段(`start_period` 以内)每秒探一次,数据卷已存在时从 6.2 s 降到 2.1 s。这个字段要 Docker Engine 25 以上。第一次启动的大头是 MySQL 初始化。
- `up -d` 返回后的头几毫秒,gameserver 进程可能还没开始监听。这时 docker-proxy 已经在宿主机端口上接受了连接,转发进容器时被拒,bot 看到 `connection reset by peer`,100 ms 后重试就成功。
- 冷启动的 gameserver 日志里没有一次 `account store unavailable` 或 `NO_ACCOUNT`,说明 MySQL 的 healthcheck 没有在建表脚本跑完之前就报 healthy(D26)。

### 依赖故障和优雅退出(D26)

compose 全套运行中,用 `docker compose stop / start` 依次停掉、再起来 Redis 和 MySQL,每一步都试一次登录:

| 操作 | 新登录 |
|---|---|
| 停掉 Redis | `UNAVAILABLE` |
| 再起来 Redis | 5 ms 后成功 |
| 停掉 MySQL | `UNAVAILABLE` |
| 再起来 MySQL | 856 ms 后成功 |

整个过程 gameserver 没有退出、没有重启,`RestartCount` 一直是 0,启动时间也没变。日志里只有对应的警告:`session store unavailable`、`account store unavailable`。

`docker compose stop gameserver` 用了 522 ms,退出码 0(不是 SIGKILL 的 137)。日志最后一行是 `gameserver stopped`,说明走完了优雅关停(D5b)。

### Ticker 准点与 Sleep 漂移(B4.1 / B4.2)

一个 30 行的独立程序,不在仓库里,逻辑如下,跑 3 次:

```go
t := time.NewTicker(50 * time.Millisecond)      // B4.1:600 次,记录 |实际醒来 − (start + k·50ms)|
for k := 1; k <= 600; k++ { <-t.C; lat = append(lat, abs(time.Since(start.Add(k*50ms)))) }

for range 600 { busy(2 * time.Millisecond); time.Sleep(50 * time.Millisecond) }  // B4.2:总耗时 vs 理想 30 s
```

| 次 | Ticker 晚到 p50 / p99 / max | Sleep 循环多用的时间 | Sleep 循环实际频率 |
|---|---|---|---|
| 1 | 0.60 / 1.08 / 1.11 ms | +1.313 s(4.4%) | 19.16 Hz |
| 2 | 0.56 / 1.61 / 2.27 ms | +1.328 s(4.4%) | 19.15 Hz |
| 3 | 0.59 / 1.29 / 5.28 ms | +1.322 s(4.4%) | 19.16 Hz |

Ticker 每次都会晚一点(WSL2 上空载时约 0.6 ms,我认为主要是叫醒睡眠线程的时间),但不累积;Sleep 循环每一轮都多出干活的 2 ms 和唤醒延迟,600 轮累积多了 1.3 s。这是 tick 用 Ticker 的依据(D20)。

## 还没测的

- **bot 和服务端分两台机器**:10000 连接那一档两个进程合计用了 12.7 核,bot 自己的延迟占多少,要分开才知道。
- **原生 Linux**:这里的数字全在 WSL2 上测。原生 Linux 上宿主机 127.0.0.1 就是内核 loopback,预计接近容器内的数字,没验证过。
- **10000 以上**:种子账号只有 1–10000。要往上测,得先加种子账号,再把 bot 放到另一台机器上。
