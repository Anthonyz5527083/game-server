# DECISIONS

每个设计决定一条,按模块排,代码注释里引用的就是这里的编号(D4、D12b……)。每条回答三个问题:

- **为什么是这个**
- **为什么不是别的**(别的写法会怎样)
- **什么时候会换**(什么条件下这个决定不再成立)

---

## 网关

### D0 语言:Go

**决定**:服务端和 bot 都用 Go。网关层只用标准库 + protobuf 运行时。

**为什么是这个**
- `net` / `bufio` / `encoding/binary` / `log/slog` / `context` 覆盖了网关层的全部需求,不用选第三方网络框架。
- goroutine-per-connection 跟「每个客户端一条长连接、彼此独立」的模型天然对应:每条连接就是一段顺序代码,不用手写状态机。
- 编译成单个静态二进制,Docker 运行镜像可以很小。

**为什么不是别的**
- C++:性能上限更高,但 epoll / Reactor、内存管理、构建系统都要自己搭,6 周做不到同样的完成度和测试覆盖。
- Java + Netty:生态成熟,但这个项目要讲清楚的是连接模型和调度,Netty 把这层封装掉了。

**什么时候会换**:单进程扛不住、要榨每一个 CPU 周期(比如 MMO 的 AOI 计算)时,热点模块换 C++。这个项目的规模(500 连接、8 人房)远到不了那一步。

**要能讲清的一点**:goroutine-per-connection 底层仍然是 epoll(runtime 的 netpoller)。区别是 Go 把「事件回调」变成了「阻塞式的顺序代码」,复杂度从业务代码里的状态机挪到了 runtime 调度器里。

### D1 消息类型放在 Envelope 的 oneof 里,不放帧头

**决定**:帧 body 永远是 `Envelope{seq, oneof payload}`,新消息只往 oneof 加字段。字段号按模块分段:10–19 网关,20–29 登录,30–39 房间,40–49 同步。

**为什么是这个**
- 一次 `proto.Unmarshal` 同时拿到类型和内容,Go 里 `switch env.GetPayload().(type)` 是类型安全的。
- 协议目录就是 `.proto` 文件本身,不用另外维护「type id → message」的注册表,两端不会对不上。
- 字段号分段,看 diff 就知道改的是哪个模块。

**为什么不是别的**:帧头放 `uint16 msg_type` + 裸 payload,能省 Envelope 的几个字节和一次很小的解码,但要手工维护注册表,两端各写一份 switch。省下的开销在本项目的量级下测不出来(B1.2:解码一帧 Ping 约 200 ns)。

**什么时候会换**:火焰图里 Envelope 解码占比显著时(500 连接压测实测:解码占服务端 CPU 的 5.5%,不显著,见 BENCHMARK);或者网关要做「不解 body 就转发」的纯路由层时,type id 放帧头才有意义。

`seq` 和 `client_time_ms` 看着重复,职责不同:`seq` 用来配对请求和应答(任何消息都能用);Ping 的 `client_time_ms` 由 Pong 原样带回,客户端不保存任何状态就能算 RTT,bot 开 500 连接时省掉 500 张表。

### D2 帧格式:4 字节大端长度前缀,上限 64 KiB

**决定**:`[len: uint32 BE][body]`,len 只计 body。body 为 0 字节是协议错误;超过 64 KiB 直接断开。实现在 `internal/gateway/codec.go`。

**为什么是这个**
- TCP 是字节流,没有消息边界(本机实测:两条消息一次 `Read` 拿到;200000 字节被拆成 53 次 `Read`)。长度前缀是最简单的定界方法:读 4 字节就知道还要读多少,O(1)。
- 4 字节不是 2 字节:2 字节的上限正好 64 KiB,和 MaxFrameSize 撞在一起没有余量。多 2 字节对一帧 Ping(15 字节)是 13%,对 8 人快照可以忽略。
- 大端是网络字节序的惯例,抓包工具默认按大端显示。
- 上限是安全措施:没有它,对端发一个 `0xFFFFFFFF` 就能让服务端分配 4 GiB。校验写在 `make` 之前,有测试盯着(`TestReadFrameRejectsBeforeAllocating`)。
- 零长度帧算错:合法的 Envelope 至少有一个 payload,body 不可能是 0 字节。

**为什么不是别的**
- 分隔符(比如 `\n`):protobuf 是二进制,body 里什么字节都可能出现,要转义,又慢又容易错。
- 定长帧:Ping 十几字节、快照上百字节,定长会浪费带宽。
- varint 长度(protobuf 的 delimited 写法):省 1–3 字节,但必须逐字节读长度,代码更绕,收益在这个量级看不见。

**什么时候会换**:要传大块数据(回放文件、地图)时,不是改上限,而是分块传输;要跟别的语言的客户端对接时,格式不变,只要两边对齐。

### D3 生成的 `.pb.go` 入库

**决定**:`internal/pb/game.pb.go` 跟 `.proto` 一起 commit。改 `.proto` 后跑 `make proto`。

**为什么是这个**:别人 clone 下来不装 protoc 也能 `go build`,README 的「怎么跑」少一步。生成代码的 diff 也能在 review 里看到协议改动的实际效果。

**为什么不是别的**:不入库的话,每个使用者和 CI 都要装同版本的 protoc 和 protoc-gen-go,版本不一致还会生成不同的代码。

**什么时候会换**:proto 文件多到生成代码的 diff 淹没 review 时,改成 CI 里生成 + 检查「生成结果和入库的一致」。

### D4 每连接读 / 写两个 goroutine,写走有界队列,队列满就断开

**决定**:`readLoop` 独占读端,`writeLoop` 独占写端。`Conn.Send` 只是往发送队列(默认 256 帧)投递,不阻塞;队列满了就断开这条连接。实现在 `internal/gateway/conn.go`。

**为什么是这个**
- 写只发生在一个 goroutine 里,所以 `net.Conn` 不用加锁,两帧的字节也不会交错。
- 广播方(房间、tick 循环)调 Send 永远不会阻塞,一个慢客户端拖不住整个房间。
- 队列满说明客户端已经落后几秒:256 帧在 20Hz 下是 12.8 秒的快照。这种客户端留着也没法玩,不如断开让它重连。

**为什么不是别的**
- 直接在调用方 goroutine 里 Write:`net.Conn` 的并发 Write 是安全的,但会阻塞;对端不读时,广播循环就卡在这个人身上,房间里其他 7 个人一起卡。
- 队列满时阻塞:同上,慢客户端拖慢所有人。
- 队列满时丢这一帧:对快照来说可以接受(下一帧会覆盖),但对请求 / 应答不安全,客户端会永远等不到应答。

**什么时候会换**:有了 20Hz 快照之后,可以分两类:快照允许丢旧帧(只保留最新的一帧),应答不允许丢,那时这里要拆成两个队列,或者给帧打「可丢」标记。现在没拆:快照是全量的,但 256 帧的队列在 20Hz 下是 12.8 秒的缓冲,落后这么多的客户端留着也没法玩;500 连接压测里没有一条连接因为队列满被断开。等真的出现「网络抖一下就被踢」再拆。

**相关的两个细节**
- `SendAndClose`:踢人时先把原因帧写出去再断。实现是往队列里放一个带 `closeAfter` 标记的帧,writeLoop 写完它就断开;它前面排队的帧照常先写(FIFO)。直接 Close 的话,客户端只看到连接断了,不知道为什么。
- `Handler` 的 OnOpen / OnMessage / OnClose 都在这条连接的读 goroutine 上按顺序调用。连接可能被别的 goroutine 关掉(比如广播时发现队列满),但 OnClose 不在那个 goroutine 里跑,而是读 goroutine 被唤醒后再跑。好处是上层处理同一条连接时不用担心「消息和断线并发」,也不会出现「广播方持锁 → 触发关闭 → OnClose 再去拿同一把锁」的死锁。

### D5 idle 检测:每帧重设 read deadline

**决定**:读循环每读一帧之前调 `SetReadDeadline(now + IdleTimeout)`。超时时 `Read` 返回 timeout 错误,读循环退出,原因记为 idle timeout。

**为什么是这个**:不用额外的 goroutine 或 timer。`SetReadDeadline` 不是系统调用,只改 runtime netpoller 里的定时器,每帧调一次的开销可以忽略。超时就是读失败,和其它断线走同一条清理路径。

**为什么不是别的**
- 每条连接一个 `time.Timer`,收到帧就 Reset:能做到同样的事,但多一个要管理生命周期的对象,超时回调在另一个 goroutine 上跑,还要处理和读循环的并发。
- 只用 TCP keepalive:它只能发现「对端机器没了」,发现不了「对端进程还在但卡住了 / 不发数据了」。而且 Linux 默认 2 小时才开始探测。
- 只在连接建立时设一次 deadline:到点就踢,不管中间有没有心跳。

**什么时候会换**:要区分「多久没收到心跳」和「多久没收到业务消息」两种超时(比如挂机检测)时,业务那一层另起 timer。

### D5b 关停:Serve 等所有连接的 OnClose 跑完才返回

**决定**:ctx 取消后,Serve 关 listener、关所有连接,然后 `WaitGroup.Wait()` 等每条连接的读写 goroutine 退出,最后才返回。Accept 出错(比如 fd 用尽)时退避重试,不退出。

**为什么是这个**:OnClose 里要删 Redis 会话、退出房间(房间解散时还要排队写战绩)。如果 Serve 不等就返回,main 退出,进程被杀,清理做到一半。Accept 重试和 `net/http.Server` 的做法一致:fd 用尽是暂时的,整个服务退出更糟。

**为什么不是别的**:不等的话关停更快,但 Redis 里会留下一批「幽灵在线」的会话,只能靠 TTL 过期。

**什么时候会换**:连接多到 OnClose 清理要很久时,给等待加上限(比如 10 秒,对应 `docker stop` 的默认宽限期),超时就放弃。

## 登录 + 会话

### D6 token:无状态 HMAC 签名

**决定**:`base64url(playerID | 过期时间) "." base64url(HMAC-SHA256(密钥, 前半段))`。游戏服只要有密钥就能校验,不查任何存储。实现在 `internal/auth`,只用标准库。

**为什么是这个**
- 校验是纯 CPU 运算(一次 HMAC),不依赖 Redis:Redis 挂了,至少「token 对不对」这一步不受影响。
- 签发方(账号服务,开发时是 `cmd/tokengen`)和校验方只共享一个密钥,不共享数据库。
- 三个细节都有测试盯着:先验签名再解析内容(签名没过的字节一个都不信);签名用 `hmac.Equal` 常数时间比较(否则能按响应时间逐字节猜签名);base64 用 `Strict()` 解码(默认解码器会忽略最后一个字符的 2 个填充位,同一个签名能写成好几种字符串。这个坑是测试连跑时撞出来的)。

**为什么不是别的**
- 随机串存 Redis 查表:能随时吊销,但每次登录多一次 Redis 查询,而且 Redis 挂了就完全登录不了。
- JWT:功能上一样,但要引一个库;JWT 的 header 能指定算法,历史上出过 `alg: none` 之类的漏洞。这里只有一种算法,自己写 30 行更容易讲清楚。

**什么时候会换**:要「立刻吊销某个 token」(封号、改密码后踢掉所有设备)时,无状态 token 做不到,要么加一张 Redis 黑名单,要么换成有状态 token。要轮换密钥时,在 token 前面加版本号(`v2.`),新旧密钥并存一段时间。

### D7 会话:内存是权威,Redis 是镜像

**决定**:「玩家 → 哪条连接」存在进程内存的 `players` 表里,所有路由(顶号、房间广播)都查它。Redis 里的 `gs:session:{pid}` 是给外部看的在线状态,带 TTL。

**为什么是这个**
- 连接(`*gateway.Conn`)是进程内的对象,本来就放不进 Redis。路由必须查内存。
- Scope 要求在线状态落 Redis:别的进程(以后的账号服务、运维脚本)不连游戏服也能查谁在线。
- 先写 Redis、成功了再改内存:Redis 失败时内存没变,回 `UNAVAILABLE`,客户端可以直接重试,不会出现「内存里登录了、Redis 里没有」的半成品。

**为什么不是别的**
- 只放内存:单进程够用,但 scope 要求的「在线状态落 Redis」就没有了;多实例时也没法查一个玩家在哪个实例上。
- 以 Redis 为权威、每条消息都查 Redis:每条消息多一次网络往返,Redis 一抖整个游戏都卡。

**什么时候会换**:多实例部署、玩家要跨实例找人(私聊、组队)时,Redis 里的 owner 就成了路由表的一部分,要认真处理「两个实例同时认为自己持有某个玩家」的竞争,那时要用分布式锁或者把登录收到一个服务里。

**续期**:一个 goroutine 每 TTL/3 用一次 MULTI/EXEC 覆盖写所有在线玩家(TTL 默认 60 秒,即每 20 秒一次)。没有选「每个 Ping 续一次」:500 人每 5 秒一个 Ping 就是每秒 100 次 Redis 往返,批量续期是每 20 秒 1 次。覆盖写而不是只 EXPIRE,所以 Redis 重启丢了数据,下一轮就补回来(有测试)。

### D8 顶号:新登录踢掉旧连接

**决定**:同一账号在第二条连接上登录时,新连接登录成功;旧连接先收到 `Kick{reason: "replaced"}` 再被断开。

**为什么是这个**
- 玩家换设备、断线后重连时,旧连接往往还没被 idle timeout 发现。拒绝新登录的话,玩家要等 30 秒才能进游戏。
- 大多数游戏都是这个行为,玩家有预期。

**为什么不是别的**:拒绝新登录能防「账号被盗后挤掉原主」,但对正常玩家体验差,而且盗号应该在账号层(密码、二次验证)解决。

**什么时候会换**:要做断线重连(选做项)时,新连接不是「踢掉旧的重新开始」,而是「接管旧连接的房间和状态」。

**要能讲清的竞争**:旧连接的 OnClose 和新连接的登录在两个 goroutine 上。清理时必须先确认「`players[pid]` 还是我」,不是就什么都不动;Redis 里也按 owner 删(Lua 脚本里比对再删)。否则旧连接断开时会把新连接的会话删掉。这两个检查都有测试。

### D9 Redis key 设计

**决定**:`gs:session:{playerID}` → hash `{owner, login_at}`,TTL 60 秒。`owner` = `{node}#{连接 ID}`,`node` 默认是 `主机名-进程号`。

**为什么是这个**
- hash 而不是 string:以后加字段(在哪个房间、客户端版本)不用改格式。
- `gs:` 前缀:和同一个 Redis 里的其他数据分开,`SCAN gs:*` 能看到本项目的全部 key。
- owner 带进程号:进程重启后连接 ID 从 1 开始重新数,只用连接 ID 会和上一个进程的残留会话撞上。

**为什么不是别的**:用一个大 hash 存全部会话(`gs:sessions` → `{pid: owner}`):查在线人数方便(HLEN),但 hash 里的单个字段不能设 TTL,进程崩溃后残留的会话永远不会过期。

**什么时候会换**:要频繁查「当前在线人数」时,加一个计数器或 sorted set(按最后心跳时间排序),而不是 SCAN。

### D10 测试用 miniredis

**决定**:单元测试和集成测试都用 `github.com/alicebob/miniredis/v2`,一个在测试进程里跑的假 Redis。

**为什么是这个**:测试不依赖 Docker,`make test` 在任何机器上都能直接跑;每个测试一个独立实例,互不干扰;能 `FastForward` 时间测 TTL 过期,能 `Close` / `Restart` 测 Redis 宕机,用真 Redis 很难做到。

**为什么不是别的**
- 连真 Redis(没起就 `t.Skip`):最真实,但没装 Docker 的人跑测试时这些测试全部跳过,等于没测。
- 自己写一个内存版的 SessionStore 接口实现:测不到 Lua 脚本和 MULTI/EXEC 本身。

**什么时候会换**:用到 miniredis 不支持的命令(比如某些 Stream、Module 命令)时。真 Redis 的覆盖由压测补:压测时服务端连的是真 Redis(7.4.2),500 个 bot 同时登录、续期、房间镜像都走过一遍。MySQL 没有类似 miniredis 的进程内替身,所以 MySQL 的测试是连真库的集成测试(D28)。

## 房间 + 广播

### D12 并发模型:一个 Manager、一把互斥锁

**决定**:`room.Manager` 用一把 `sync.Mutex` 保护全部房间和「玩家 → 房间」索引。大厅在自己的锁里调用 Manager。锁的顺序固定为 大厅 → 房间 → 网关,没有反向调用。

**为什么是这个**
- 进出房间是低频操作(一个玩家一局几次)。B3.2 实测:一把锁下快速匹配 + 离开,4 核和 20 核并发时每对操作约 0.92–0.97 µs,也就是每秒约 100 万次。500 人的需求是每秒几十次,差了四个数量级。
- 多步操作天然原子:「检查容量 + 加入」不会让两个人同时抢到最后一个位置(64 个 goroutine 抢 7 个空位,测试 20 轮都恰好 7 个成功);「最后一个人离开 + 销毁房间」不会让第三个人加入一个正在销毁的房间。
- 不用 RWMutex:几乎所有操作都要写(加入、离开),读多写少的前提不成立,RWMutex 自己的簿记开销反而更大。

**为什么不是别的**
- 每个房间一把锁:房间内的操作可以并行,但快速匹配要跨房间找空位,跨房间操作就得按固定顺序拿多把锁,死锁风险和代码复杂度都上去了,而锁竞争本来就不是瓶颈。
- 每个房间一个 goroutine(actor + channel):房间状态只有一个 goroutine 碰,完全不用锁,tick 也能直接放进这个 goroutine 的 select 里。代价是每个请求要走「发 channel → 等回复」两次调度,快速匹配仍然需要一个全局协调者。加 tick 时重新考虑过,最后选了折中(D12b)。

**什么时候会换**:加了每房间 20Hz 的 tick 之后。如果 tick 也拿这把全局锁,63 个房间 × 20Hz = 每秒 1260 次加锁,还是远低于上限;但一个房间 tick 慢了会拖住所有房间,tick 里一旦有重计算(碰撞、AI)就不行。所以加 tick 时把房间内的游戏状态挪到了每个房间自己的锁里,全局锁只管成员关系(D12b)。

---

### D13 Redis 里的房间是镜像,异步同步

**决定**:内存里的房间是权威。Redis 里存 `gs:rooms`(所有房间号的 set)和 `gs:room:{id}`(成员的 set)。变化记进 dirty 集合,由一个镜像 goroutine 异步写 Redis。启动时、每 30 秒、停止时各做一次全量覆盖。只有一个进程写这些 key。

**为什么是这个**
- 进出房间是在大厅锁里做的,不能在锁里等 Redis 的网络往返。
- dirty 集合天然合并:8 个人陆续进同一个房间,只需要同步最后的样子。镜像 goroutine 醒来时在锁里拍快照,在锁外写 Redis;快照总是最新的,所以重试时不会把旧数据写回去。
- 写失败就重新标脏,一秒后再试,Redis 恢复后自动追上(有测试)。
- 全量覆盖解决三个问题:启动时清掉上一个进程(可能是崩溃的)留下的房间;Redis 重启丢了数据能补回来;关停时最后同步一次空状态,不留残留。

**为什么不是别的**
- 以 Redis 为权威、每次进出房间都同步写:每次操作多一次网络往返,而且要在锁里等它,Redis 一抖所有人都进不了房间。
- 进程重启后从 Redis 恢复房间:恢复出来的房间里的玩家连接全断了,恢复一个没有连接的房间没有意义,不如清掉。

**什么时候会换**:多实例部署时,key 要带上 node(`gs:{node}:room:{id}`),全量覆盖只覆盖自己的;要支持「服务端重启后玩家重连回原房间」时,Redis 才需要变成权威,那时房间状态的每次变化都要持久化。

### D14 广播:编码一次、持锁发送

**决定**:房间事件只编码一次,所有成员共享同一个 `[]byte`。在 Manager 的锁里调用每个成员的 `SendFrame`。

**为什么是这个**
- 共享 `[]byte`:8 个人不用编码 8 次、拷贝 8 份。B3.1 实测:2 人房和 8 人房每次进出的分配次数都是 13 次,不随人数涨。前提是 `SendFrame` 拿到 frame 之后不改它(网关只读它、写进 socket)。
- 持锁发送:`SendFrame` 不阻塞(往有界队列投递,满了就断开对方),持锁只多花几微秒。换来的是事件顺序和房间状态的变化顺序严格一致。放到锁外发的话,两个人同时加入,第三个人可能先收到「C 进来了,房间是 [A B C]」,再收到「B 进来了,房间是 [A B]」,他看到的房间就倒退了。`TestEventsAreOrdered` 盯着这一点。

**为什么不是别的**:锁外发送(先拷一份成员列表,放锁,再发),锁持有时间更短,但要给事件加版本号,让客户端丢弃旧事件。在锁竞争不是瓶颈的前提下,不值得把复杂度推给客户端。

**什么时候会换**:`SendFrame` 变成可能阻塞的实现时(比如改成同步写),持锁发送就会让一个慢客户端卡住所有房间,必须改成锁外发送 + 版本号。所以 `room.Sender` 接口的注释里写明了「必须不阻塞」。

### D15 慢客户端:房间层不另定规则

**决定**:房间广播时某个成员发送失败(队列满、连接已关),直接跳过它,不重试、不在房间层踢人。网关在队列满时已经断开了它(D4),它的 OnClose 会走正常的离开流程,房间里其他人收到 LEFT。

**为什么是这个**:一个规则只在一个地方实现。网关负责「连接跟不上」,房间负责「谁在房间里」,两层不重复判断。

**为什么不是别的**:房间层自己维护「连续 N 次发送失败就移出房间」:和网关的判断重复,还可能和网关的关闭流程竞争(网关正在关,房间又移了一次)。

**什么时候会换**:如果决定快照可以丢(只保留最新的一帧),那是网关里要区分「可丢帧」和「不可丢帧」(D4 的「什么时候会换」),房间层仍然不用改。tick 广播快照也沿用了这条规则:发送失败直接跳过。

## 同步

### D12b tick 的并发:每个房间一个 goroutine,房间自己一把锁

**决定**:建房时给房间起一个 tick goroutine,销毁时 `close(stop)` 让它退出。房间的游戏状态(`sim.World`)由房间自己的锁保护,tick 只拿这把锁,不碰 Manager 的全局锁。成员列表写的时候两把锁都拿,读的时候拿任意一把。锁顺序 Manager → 房间 → 网关。实现在 `internal/room/tick.go`。

**为什么是这个**
- 这是 D12「什么时候会换」的那一步。tick 如果拿全局锁,63 个房间 × 20Hz 的 tick、所有进出房间、每秒一万条移动输入都在一把锁上排队。锁本身扛得住(B3.2:每秒约 100 万次),但一个房间 tick 慢了会拖慢所有房间。分成两层之后,房间之间没有共享状态,tick 互不等待。
- 每个房间一个 goroutine,不是一个全局 goroutine 轮流 tick 所有房间:轮流的话第 63 个房间永远比第 1 个晚,一个房间卡住所有房间都卡。goroutine 起步 2 KiB 栈,63 个可以忽略。
- 成员列表「写两把、读一把」:进出房间(持全局锁)要读成员列表广播 JOINED / LEFT,tick(持房间锁)要读成员列表发快照,两边都不用再多拿一把锁。
- 移动输入走 `Manager.Input`:在全局锁里查到房间就放锁,再拿房间锁。持着全局锁去等房间锁的话,房间锁正被 tick 占着时,所有房间的进出和输入都排在这一个房间后面。放锁的空档里玩家如果离开了,world 里找不到他,这条输入作废,不会写错房间。
- 进房间时成员列表、world 和 JOINED 事件在同一段房间锁里完成:房间里的人一定先收到「X 进来了」,再收到带着 X 的快照。

**为什么不是别的**
- tick 拿全局锁:最简单。代价是上面说的互相拖累,tick 里只要多做一点计算,进出房间就要等。
- 每个房间一个 actor(goroutine + channel,完全不用锁):房间状态只有一个 goroutine 碰,很干净。但快速匹配要跨房间找空位,还是要一个全局协调者;每条输入都走一次 channel 发送和调度,每秒一万条比加一次锁贵。现在的 tick goroutine 其实是半个 actor,只是输入走锁不走 channel。

**什么时候会换**:房间里的计算变重(碰撞、AI、技能结算),tick 耗时到毫秒级时,输入改成写进一个缓冲区,tick 开头在锁里把缓冲区整个换出来,读 goroutine 就完全不用等 tick。

### D16 输入是「方向」,同一个 tick 收到多个只取最后一个

**决定**:`MoveInput` 表示「现在按着哪个方向」,不是「走一步」。服务端给每个玩家只存最近收到的一条,下一个 tick 才应用;方向持续生效,直到收到新的方向(停下就发 0,0)。

**为什么是这个**
- 累加的话,客户端多发几条输入就能走得更快,等于把加速外挂做进了协议。只取最后一条,每个 tick 最多走 移速 × dt,灌 1000 条也一样(`TestInputFloodDoesNotSlowTick` 检查每个 tick 的位移上限)。
- 方向持续生效:客户端只在方向变化时发就够了,少到一条输入玩家也不会停住。
- 读 goroutine 只把输入记下来,不改位置。位置只在 tick 里变,同一个 tick 发给所有人的快照是同一个时间点的状态。

**为什么不是别的**
- 每条输入就是一步,按 seq 逐条应用:帧同步里常见,要求服务端按固定节拍消费输入,客户端发快了要排队、发慢了要补空。状态同步不需要这么严。
- 输入一到就改位置:位置更新的时刻取决于消息到达的时刻,先到的人先动,快照里各人的位置不是同一时刻的。

**什么时候会换**:要加技能、开火这类离散动作时,它们不能「只取最后一个」,要另开一个按顺序排队的消息类型。

---

### D17 状态同步,不是帧同步

**决定**:服务端权威。服务端算所有人的位置,每个 tick 把结果(快照)发给房间里所有人;客户端只发输入、只画快照。

**为什么是这个**
- 作弊空间小:客户端改不了位置,只能发输入,输入的长度还被截到 1 以内(`sim.ClampDir`),NaN / Inf 当成 0。
- 中途加入、断线重连简单:进来的人下一个 tick 就收到全量状态,不用回放历史输入。
- 不要求确定性:客户端可以是任何语言、任何浮点实现。帧同步要求所有客户端算出逐位相同的结果,跨平台的浮点差异会导致不同步,而且很难定位。

**为什么不是别的**:帧同步(lockstep)只广播输入,每个客户端自己算。带宽只和输入有关,和单位数无关,适合 RTS 这种几百个单位的游戏。代价是必须确定性;要等最慢的人,或者做预测 + 回滚;每个客户端都有全量状态,透视挂没法防。

**代价**:下行带宽随房间人数平方增长(每人的快照里有 N 个人,发给 N 个人);服务端要算所有人的逻辑;客户端看到的是半个 RTT 之前的状态,不做预测的话自己的操作有延迟感(D19)。

**什么时候会换**:单位多到全量快照装不下(RTS),或者要求所有客户端逐帧一致(格斗游戏的回滚网络)。

---

### D18 快照发全量

**决定**:每个 tick 发房间里所有人的完整状态,不做增量。

**实测**(`TestSnapshotSize8`,tick 编号和 last_input_seq 取压测 30 秒左右的量级):8 人快照一帧 149 字节(body 145 字节)。下行带宽 = 149 B × 20 Hz × 8 人 = 每个房间 23.8 KB/s,每个玩家 2.98 KB/s;500 人 63 个房间一共约 1.5 MB/s。

**为什么是这个**
- 149 字节已经很小。增量最多把它压到几十字节,每个玩家每秒省两 KB,这个量级没有意义。
- 全量没有状态:客户端刚进来、或者漏了一帧,下一帧就完整了。增量要记住每个客户端确认到了哪一帧,丢包、重连都要重发基准帧。
- 传输是 TCP,不丢包。增量最大的好处是 UDP 下少重传,这里用不上。
- 用 `float` 不用 `double`:场地 100 × 100,float32 的精度到 0.00001 量级,每个坐标省 4 字节。

**为什么不是别的**:增量 / 差分快照,只发变了的实体和字段(Quake 3 的做法),适合实体多、走 UDP 的游戏。

**什么时候会换**:单房间的实体多到快照上 KB(64 人、带子弹)时,先做视野裁剪(AOI,只发附近的人),再考虑增量。

### D19 last_input_seq:留给客户端预测和对账

**决定**:快照里每个玩家带 `last_input_seq`,表示服务端已经把这个玩家的输入应用到了哪一条。现在的客户端不用它。

**将来怎么用**(客户端预测 + 服务端对账):
1. 客户端每发一条输入,就立刻在本地用同样的 `Step` 走一步(预测),同时把这条输入放进「待确认」队列。
2. 收到快照时,把自己的位置重置成快照里的权威位置,丢掉队列里 seq ≤ last_input_seq 的输入(服务端已经算进去了),再把剩下的输入在本地重新应用一遍。
3. 效果:自己的操作没有 RTT 的延迟感;服务端不同意时(撞到边界、被截速)会被拉回去。别人的位置用插值,在最近两个快照之间平滑移动。

**为什么现在不做**:得有一个真正画出来的客户端才看得到效果。服务端要做的只有这一个字段,先放进协议,以后不用改协议。`sim` 是纯函数(D20),用 Go 写的客户端可以直接复用 `Step` 做预测,保证两边算法一致。

### D20 step 是纯函数;tick 用 Ticker + 固定 dt

**决定**:`sim.Step(pos, dir, dt)` 和 `World.Advance(dt)` 不读时钟、不碰锁和网络。tick 循环用 `time.Ticker`,每次传固定的 dt = 50ms,不用实际经过的时间。

**为什么是这个**
- 纯函数能表驱动测试:给定位置、方向、dt,结果是确定的。测试不用 Sleep,也不会因为机器慢偶尔失败(`TestStep`、`TestClampDirSameDistance`)。
- 固定 dt:位置只取决于 tick 数,不受调度抖动影响。同样的输入序列在哪台机器上跑都是同样的结果,这也是 D19 客户端预测的前提。
- Ticker 不用 Sleep(B4.2 实测):`for { 干活 2ms; Sleep(50ms) }` 跑 600 次,多用了 1.31–1.33 秒(慢 4.4%,实际 19.2 Hz),因为每一轮都多出干活的时间和唤醒延迟,而且是累积的。Ticker 按「上一次的预定时刻 + 50ms」排下一次,误差不累积:B4.1 空载时每次醒来比理想时刻晚 p50 0.56–0.60 ms、p99 1.1–1.6 ms,但不会越来越晚。

**为什么不是别的**
- 变步长(dt 用实际经过的时间):醒晚了多走一点,看起来更准,但结果依赖调度,同一组输入每次跑出来的位置都不同,测试只能比个大概。
- tick 里直接读 `time.Now()` 算位置:同上,而且测试必须真的等时间过去。

**代价**:Ticker 的 channel 只有 1 格,接收方太慢时会丢 tick;固定 dt 下丢一个 tick 等于游戏时间慢了 50ms。现在 tick 耗时 p99 几十微秒(B5.4),离 50ms 很远;真发生了,tick 准点直方图里能看到。

### D21 每个指标的类型

| 指标 | 类型 | 为什么 |
|---|---|---|
| `gameserver_connections`、`gameserver_players_online`、`gameserver_rooms` | gauge(`GaugeFunc`) | 当前值,能升能降。抓取时现算(调 `Count()` / `Online()`),不在每次上下线时加减,不会和真实状态对不上 |
| `gameserver_messages_total{dir, type}` | counter | 只增不减,QPS 用 `rate()` 算。进程重启归零,`rate()` 能识别 |
| `gameserver_tick_duration_seconds` | histogram | 要看分布(p50 / p99),平均值看不出偶尔的慢 tick |
| `gameserver_tick_lateness_seconds` | histogram | tick 实际醒来比理想时刻晚多少,对应 B4.1 / B5.5 |

另外默认 registry 自带 `go_goroutines`、`go_gc_*`、`process_resident_memory_bytes` 等,资源数据(B5.6)从这里读。

**为什么不用 summary**:summary 在进程里把分位数算好再暴露,看着省事,但多个实例的分位数没法合并(两个 p99 取平均不是 p99),分位数和时间窗口也在代码里写死了。histogram 只暴露每个桶的计数,桶能跨实例相加,分位数在查询时用 `histogram_quantile` 算。代价是精度取决于桶怎么划(D22)。

**标签**:消息计数按方向 × payload 类型(2 × 13),基数固定。不能用玩家 ID 或房间号做标签:时间序列的数量会随玩家数增长,把 Prometheus 撑爆。每个组合在启动时预先建好、按字段号查数组,每条消息不用拿 label 字符串去哈希。

### D22 histogram 的桶

**决定**:tick 耗时的桶是 1、2.5、5、10、25、50、100、250、500 µs,1、5、25 ms;tick 准点的桶是 50 µs 到 50 ms。

**为什么是这个**:默认桶是 5 ms 到 10 s,给 HTTP 请求用的。tick 耗时正常是几微秒(B5.4:p50 落在 5–10 µs),用默认桶的话所有样本都在第一个桶里,分位数什么也看不出来。桶按 1–2.5–5 的倍数排,每个数量级 3 个,相对误差不超过 2.5 倍,判断「p99 < 1 ms」足够。上限到 25 ms,是 50 ms 预算的一半,过了这条线就该报警。准点直方图到 50 ms,超过就是整整晚了一个 tick。

**代价**:分位数只能精确到桶。BENCHMARK 里 tick 耗时报的是「p99 落在哪个桶」加上桶内线性插值的估计,不是精确值。要精确值得在客户端量(botclient 的快照间隔),或者换 Prometheus 的 native histogram。

### D23 分位数用最近秩;样本量

**决定**:botclient 的分位数一律用最近秩:排序后取 `sorted[ceil(p·n) − 1]`,不插值。

**为什么是这个**:最近秩取的是一个真实出现过的样本,「p99 = 99% 的样本不超过它」,可以直接解释。插值在样本少时会编出一个没出现过的值。样本量:一次压测 500 × 5 Hz × 30 s = 75,000 个 RTT 样本,p99 由第 74,250 个决定,比它慢的还有 750 个,换一次跑也不会跳太多;快照间隔每次约 30 万个样本。B1.3 那种 5000 个样本的冒烟,p99 只由最慢的 50 个决定,所以只算冒烟。

**为什么看 P99 不看平均**:一个玩家每秒收 20 个快照、发 5 个 Ping,一分钟 1500 次交互,p99 意味着每分钟碰上 15 次这么慢。平均值会被大量快样本稀释,看不出这些卡顿。

**open-loop**:Ping 按 ticker 发,不等上一个 Pong。等回来再发(closed-loop)的话,服务端卡住时 bot 也停了,慢样本采不到,P99 会好看得不真实(coordinated omission)。

**随机相位**:每个 bot 开始发之前先等一个随机时长(0 到 200 ms)。第一版没有这一步,500 个 bot 的 ticker 相位对齐,每 50 ms 同时发出 500 条:服务端只用了 0.4 个核,RTT 却随连接数线性涨,量到的主要是这一波突发的排队时间(BENCHMARK「第一版」)。真实玩家的发送时刻是随机的,压测客户端也应该是。

### D24 依赖:Prometheus 官方 Go 客户端

## 持久化:MySQL

### D28 账号和战绩放 MySQL;驱动用 go-sql-driver/mysql

**决定**:
- `accounts(player_id PK, name, created_at)`:登录时 token 验签通过之后,再按主键查一次账号存不存在。
- `match_records`:一局一行。一局 = 一个房间从建立到最后一个人离开;记房间号、起止时间、tick 数、峰值人数,玩家列表存 JSON 数组。`(room_id, started_at)` 唯一。
- 驱动用 `github.com/go-sql-driver/mysql`,走标准库 `database/sql`,不用 ORM。DSN 从环境变量 `GS_MYSQL_DSN` 读,不设就不查账号、不记战绩。
- 建表脚本 `deploy/mysql/init.sql`,全部可以重复执行;compose 第一次起 MySQL 时自动执行。

**为什么是这个**
- 账号和战绩是「要长期留着、要按条件查」的数据,Redis 里的东西是「丢了能重建」的在线状态。两者分开存,Redis 可以随便重启。
- 先验签名再查库:签名不对的请求一次数据库查询都不花。查不到回 `NO_ACCOUNT` 并断开;查询出错(MySQL 不通)回 `UNAVAILABLE`、连接保留。这两种必须分开,前者重试没用,后者重试有用。
- 战绩异步写:房间解散发生在两把锁里,只能往一个有界队列里投递(满了丢一条并打日志),由单独的 goroutine 写库、失败重试 3 次。在锁里等数据库,会让所有人进出房间都卡在一次写上。
- 唯一键让重试幂等:写入超时时,上一次可能其实已经写进去了。房间号每次进程重启从 1 开始,单靠 `room_id` 不唯一,加上毫秒级的建房时间才唯一。用 `ON DUPLICATE KEY UPDATE id = id`,不用 `INSERT IGNORE`:后者会把类型溢出之类的错误也降级成警告。
- 关停时正在写的那一条要写完:第一版把关停用的 ctx 直接传给了写入,本机连真 MySQL 测出来,关停时正在写的记录报 `context canceled`,数据库里却已经有了,重试还会写重复。现在写入用独立的 context,队列里剩下的在 5 秒内写完(`TestRecorderFinishesInflightWriteOnStop` 在旧写法上会红)。
- 玩家列表用 JSON 数组:一局一行,写一次;按玩家查战绩是低频操作,`JSON_CONTAINS` / `MEMBER OF` 够用。
- go-sql-driver/mysql 是纯 Go 的 MySQL 驱动,事实上的标准;两张表、三条 SQL,用 ORM 只会多一层要解释的东西。

**为什么不是别的**
- 账号也放 Redis:没有持久化保证(RDB / AOF 都会丢最后一段),而且 Redis 重启时所有人都登录不了。
- 战绩同步写(在解散房间的那一刻写库):见上,锁里不能等网络。
- 战绩拆成 `matches` + `match_players` 两张表:按玩家查(「我最近 20 局」)可以走索引,但每局要写 1 + N 行。现在没有按玩家查的需求。
- 测试用 sqlmock:它只能断言「发了哪条 SQL」,测不到 SQL 本身对不对、建表脚本能不能跑。MySQL 没有 miniredis 那样的进程内替身,所以存储层的测试连真库,设了 `GS_TEST_MYSQL_DSN` 才跑;大厅、房间层的测试用接口替身(`AccountStore`、`RecordSink`)。

**验证**:本机 MySQL 8.4.9 上集成测试通过(init.sql 执行两遍、查种子账号、写读战绩每个字段、同一局写两次只留一行);500 个 bot 端到端跑一遍:63 个房间 → 63 条战绩、500 个玩家,关停后 0 丢失。

**什么时候会换**:要做「我的战绩」「排行榜」时,加 `match_players(match_id, player_id)` 表并按 `player_id` 建索引;账号量大到主键查询也成负担时(百万级在线登录风暴),在 Redis 里缓存「账号存在」。

## 部署

### D25 运行镜像用 distroless/static

**决定**:多阶段构建。build 阶段 `golang:1.27-alpine`;运行阶段 `gcr.io/distroless/static-debian12:nonroot`,只放 `CGO_ENABLED=0` 编出来的静态二进制,用非 root 用户运行。

**为什么是这个**
- Go 二进制是静态链接的,运行时不需要 libc,也不需要编译器:运行镜像里放二进制就够了。
- distroless/static 里只有 CA 证书、时区数据和 `/etc/passwd`(有 nonroot 用户),没有 shell、没有包管理器。镜像里能被利用的东西越少越好。
- 三个二进制(gameserver、botclient、tokengen)都放进去,容器里可以直接 `docker compose exec gameserver botclient ...` 做冒烟测试,不需要 shell。
- `-trimpath -ldflags="-s -w"` 去掉构建机路径和符号表,三个二进制一共 22 MB(本机实测,gameserver 12.5 MB)。去掉符号表之后 pprof 照样能解析函数名(用的是 runtime 的 pclntab,本机验证过)。

**为什么不是别的**
- alpine:多几 MB,有 shell 和 apk,排障方便(能 `docker exec sh` 进去看)。代价是攻击面大一些。这个项目排障靠 admin 端口(metrics、pprof)和镜像里的 botclient,不需要 shell。
- scratch:最小,但没有 CA 证书(以后连带 TLS 的 Redis / MySQL 会失败)、没有时区数据(`time.LoadLocation` 失败)、没有用户(默认 root,要自己写数字 UID)。distroless/static 就是「scratch + 这三样」。

**什么时候会换**:线上要在容器里现场排障(抓包、看文件)时,换成 alpine 或者 distroless 的 `:debug` 变体(带 busybox shell)。

镜像体积(B6.1)还没量:开发机上还没有 Docker。

### D26 等依赖就绪:healthcheck + depends_on 管启动顺序,应用自己扛运行中的故障

**决定**:compose 里 Redis 和 MySQL 都有 healthcheck,gameserver `depends_on` 它们的 `service_healthy`。同时 gameserver 自己不依赖启动顺序:启动时连不上 Redis / MySQL 只打警告,不退出;运行中它们挂了,登录回 `UNAVAILABLE`,恢复之后自动好。

**为什么是这个**
- `depends_on` 只管第一次启动:`docker compose up` 时等依赖健康再起 gameserver,日志干净,第一个 bot 不会撞上 `UNAVAILABLE`。
- 但它管不了运行中依赖重启(单独 `docker compose restart redis`),Kubernetes 里也没有 depends_on。真正的容错只能在应用里做,而应用早就这么写了(D7:先写 Redis 再改内存,失败回 UNAVAILABLE;续期覆盖写,Redis 丢数据能补回来)。
- 应用不因为依赖不可用而退出,所以不会进入「崩溃 → 重启 → 依赖还没好 → 再崩溃」的循环。`restart: unless-stopped` 只兜真正的崩溃。
- MySQL 的 healthcheck 走 TCP(`-h 127.0.0.1`):官方镜像初始化时先起一个只听 socket 的临时实例跑建表脚本,这时 TCP ping 不通,不会在表建好之前就报 healthy。

**为什么不是别的**
- 只靠应用重试:能工作,但第一次启动时日志里会有一串连接失败的警告,看着像出了问题。
- 只靠 depends_on:依赖运行中一重启,应用就得跟着重启,而且换个编排系统就没了。
- 在应用里启动时阻塞等待依赖(连不上就一直重试、不开端口):依赖挂掉时整个服务不可用,连 Ping 都不回,健康检查和排障都更难。

**什么时候会换**:上 Kubernetes 时,healthcheck 换成 readiness probe(依赖不通时报 not ready,让流量先别进来),应用侧的容错不变。

### D27 网络:默认 bridge,端口只绑 127.0.0.1

**决定**:用 compose 的默认 bridge 网络,容器之间用服务名访问(`redis:6379`、`mysql:3306`)。映射到宿主机的端口全部写成 `127.0.0.1:端口:端口`。

**为什么是这个**
- bridge 有网络隔离:每个容器有自己的网络命名空间,只有显式映射的端口能从外面访问。Redis 没有密码、MySQL 是开发密码、admin 端口上有 pprof,都不能暴露给局域网,所以映射时只绑 127.0.0.1。
- 服务名就是 DNS 名,配置里不出现 IP。
- Docker Desktop(Mac / Windows)上 host 网络模式的支持有限制,bridge 在哪都一样。

**为什么不是别的**:host 网络模式(`network_mode: host`)直接用宿主机的网络栈,没有 NAT、没有端口映射。

**对压测数字的影响**(还没测,B6.2 要验证):bridge 模式下,从宿主机访问映射端口的包要经过 NAT,本机访问 127.0.0.1 时还可能经过 docker-proxy 这个用户态转发进程,每个包多一次拷贝和一次进程切换。BENCHMARK 里的数字是裸跑测的,服务端的 CPU 大头本来就是系统调用和调度(见火焰图),多一层转发预计会抬高 RTT。要比较得公平,压测客户端应该也放进同一个 compose 网络里跑(`docker compose run`),或者两边都用 host 网络。

**什么时候会换**:单机上追求最低延迟(压测、或者一台机器只跑一个游戏服)时用 host 网络;真实部署多半在 Kubernetes,走的是 CNI 网络,这个选择由集群决定。
